# 米哈游启动器已安装游戏检测实现方案

后续范围修订：用户要求支持 downloading。现有 games/find 同时返回 MMKV 当前记录确认的首次下载（installed=false），已安装标志仍独立核验。增加私有 download.rs，使用长度、CRC 和当前键值语义；不使用历史 JSON 搜索。当前接口行为以 [使用说明](../../hoyoplay.md) 为准，以下仅已安装范围的描述为初始设计记录。

日期：2026-10-29。状态：按用户后续“开始实现代码”要求落地当前判据。依据：[本机调研](../../hoyoplay-install-detection-research.md)、[官方来源](../../hoyoplay-official-sources-research.md)。

实施修订：用户在第二款游戏下载采样后明确要求开始实现。下文原定实现前验证项保留为尚未完成的覆盖审计，不再阻止本次代码接入；实际范围和限制以 [使用说明](../../hoyoplay.md) 为准。仅纳入 nap_cn/hkrpg_cn 官方身份快照，不推广到所有游戏。没有增加引擎启发式或进程名识别。实现不表示更新/修复/星铁完成期已经实测。

验证进度：已补充第二款游戏星穹铁道下载期样本（hkrpg_cn）。版本为空、指定 StarRail.exe 缺失、下载组件尚无本地版本提交；同一时刻绝区零保持已安装记录。星铁完成期及接近完成阶段仍待采样，此进展不改变后文发布门槛。

## 1. 目标与支持承诺

提供与现有 WeGame 相同的已安装候选检测能力：定位启动器、列出已安装游戏、按 ID 查询、返回游戏目录。检测离线、只读，不要求启动器运行，不要求管理员权限。不枚举首次安装任务、不返回未安装目录、不扫描全盘、不修改启动器记录。

平台标识统一为 `hoyoplay`，Rust 枚举为 `GameType::HoYoPlay`，GUI 显示“米哈游启动器 / HoYoPlay”。名称用于统一接入，不意味着首版已验证国际服。首版验证对象为 Windows 国服启动器 1.19.0.382；其他渠道和旧版独立启动器暂不承诺支持。

“已安装”表示有一致的本地安装提交记录及指定启动文件，不等同于全量文件校验或保证可玩。精确更新状态、下载进度、安装/启动/卸载操作和进程名均不在此方案范围内。保持现有 Game/GameState，不添加进程字段。

**发布门槛：**当前只有绝区零首次安装前后证据。下述判据为待验证设计，不能直接作为已覆盖全部游戏的实现声明。完成最小验证集前不接入对外平台入口；不以启发式兜底替代缺失证据。

## 2. 对外 Interface

```rust
pub fn executable() -> Result<PathBuf>;
pub fn games() -> Result<Vec<Game>>;
pub fn find(id: &str) -> Result<Game>;
```

- `games()` 仅返回确认已安装的候选，正常无结果返回空列表。启动器 EXE 被删除不影响仍可读取的游戏安装记录。
- `find()` 与 `games()` 使用相同判据，避免行为分叉。
- `id` 使用包含区域/渠道的 GameBiz，例如 `nap_cn`；不使用显示名、安装路径或下载包 ID。官方 game.id 仅作为内部目录信息，暂不提供 ID 别名。
- ID 语法限制为非空小写 ASCII 字母、数字和下划线，长度上限 64；非法值返回 InvalidGame；语法合法但未命中返回 GameNotFound。
- `executable()` 独立定位启动器，找不到返回 LauncherNotFound。非 Windows 沿用现有不支持平台错误约定。
- 不增加专属扫描报告、任务接口、目录配置选项或新的 FFI 函数。

结果 `_type=hoyoplay`，`name` 来自受支持的官方配置快照，`path` 为实际游戏目录，`installed=true`；commands 和 match_identity 保持空。needs_update/downloading 保持既有默认 false，字节字段为空，并明确它们在此平台未检测，不应解释为确认无更新或无下载。

## 3. 模块与内部数据流

```text
src/hoyoplay/mod.rs       对外 Interface、扫描编排、结果映射与去重
src/hoyoplay/windows.rs   注册表候选与客户端路径发现
src/hoyoplay/catalog.rs   带来源和验证范围的官方配置快照
src/hoyoplay/manifest.rs  本地配置和指定文件核验
```

四个文件共同构成一个 Module；只有 mod.rs 的三个函数对外。私有扫描入口接受候选集合，以临时目录和注册表适配测试验证同一条检测路径，不建立通用平台框架。复用现有 winreg、rusqlite 和错误约定，不为本次功能重构 WeGame。

流程：枚举注册表 → 获取 GameBiz/实际路径 → 匹配已验证配置 → 读取本地提交证据 → 检查指定文件 → 去重排序 → 映射 Game。任何不能确认的候选均不冒充已安装。

## 4. 候选发现与身份

### 游戏候选

本机已验证来源为 `HKCU\Software\miHoYo\HYP\1_1\<biz>` 的 GameBiz、GameInstallPath。遍历已支持渠道根的直接子键，显式读取 32/64 位视图并去重，不枚举其他用户注册表。

- 要求子键 biz 与 GameBiz 一致，且命中已验证目录配置。
- GameInstallPath 必须为本地绝对目录；正确处理 REG_EXPAND_SZ 和 UTF-16，不要求与启动器同盘。
- 路径不存在视为残留；空路径、相对路径、UNC 跳过。先验证类型，不把命令行解释成路径。
- 卸载项 InstallLocation 仅可用于启动器定位。本机游戏卸载项此值指向启动器，禁止将其作为游戏目录兜底。
- 不从默认安装目录、游戏名、任意 EXE 或引擎布局推导游戏身份；不枚举未登记目录。

后续若证实其他渠道使用不同注册表根，通过明确的渠道配置扩展；不能盲目尝试所有类似名字的注册表树。

### 客户端定位

优先当前用户 HYP 渠道 InstallPath 下 launcher.exe，再读取机器对应 HYP 卸载项 InstallLocation/DisplayIcon；验证文件存在，固定顺序处理重复来源。不执行命令、不依赖正在运行的 HYP.exe。命令行/图标路径解析遵循现有安全路径规则，不顺带进行公共路径解析重构。

### 官方配置快照

开发时获取官方 getGames/getGameConfigs 形成小型静态目录：biz、game.id、显示名、exe_file_name、渠道、来源 URL、采样日期、验证范围。运行时不请求远端，不下载默认路径配置。

目录项存在只代表已知身份；另以明确的已验证支持集控制可采用的安装判据。先收录身份不等于启用检测。新增支持需证据及测试，不能把绝区零特例转换成所有条目的默认规则。相对启动路径禁止绝对路径和 `..`，最终路径不得越出已验证游戏根目录。

## 5. 安装完成判据与取舍

### 主方案：注册表候选 + 游戏目录提交记录

在完成第 8 节验证后，为验证通过的渠道/游戏启用以下最小组合：

1. 存在可信注册表候选并匹配官方 biz 配置。
2. 目录 config.ini 的 `[General]` 有有效非空 game_version，channel/sub_channel 与候选渠道相符。
3. 官方配置指定的启动文件为实际存在的普通非空文件，其解析路径位于游戏根内。
4. 读取前后提交配置和候选身份保持一致；发生改变时重试一次，仍不稳定则本轮跳过并记录诊断。

game_version 只作为本地版本，不与远端最新版本要求相等。不得以固定的 3.3.0 或某个构建 ID 编码判断。版本格式宽容接受受限长度的正常版本文本，不将所有游戏强制套入语义版本格式；拒绝控制字符、空值和歧义重复键。

此组合目前仅有一次首次安装正反样本，不足以证明版本字段只在完成时提交。必须补齐“接近完成但仍在解包/校验”的样本以及第二款游戏，验证提交时机后才能启用。

### 不作为通用必要条件的证据

- chunk/staging：首次下载完成后清理已实测，但更新和修复时可能重新出现；不因目录存在就排除已有安装。
- downloading_mode：本次由 chunk 变空，语义未充分验证，暂不作为通用完成位。
- pkg_version/version_info：下载阶段已经存在，只可用于一致性研究。
- file_verify：绝区零存在成功记录，但官方仅部分游戏启用，且旧记录可残留；不作为所有游戏的必要条件，也不以成功记录覆盖缺失启动文件。
- gamedata.dat：未解析有效键值存储协议，且完成后提取版本仍为空；首版不解析，不搜索历史 JSON 片段。
- UnityPlayer.dll、GameAssembly.dll、*_Data：不参与检测。

### 下载组件数据库的角色

chunk_config.db 已观察到完成后才写入 local_version/local_build_id，属于有价值的提交证据，但包 ID/biz 的稳定关联、其他下载模式和清理后的持久性尚未验证。因此主方案不强制依赖它；目前仅用于调研交叉验证。

若第 8 节证明“配置版本 + 指定 EXE”在未完成时可同时存在，则主方案不能发布：先验证下载组件提交记录及稳定包映射，修订设计后再实现。不能直接把当前 20 行、某个包 ID 或猜测的 file_status 数值写成临时规则。

### 更新/修复语义

已安装表示已存在的本地安装提交；有新版本、预下载或后台下载不自动使其变成未安装。旧版本记录与必要启动文件存在时是否仍可确认已安装，需要更新样本验证。若无法可靠区分首次未完成与更新，不能承诺该状态覆盖；不能把 downloading=false 当作已安装，也不能把 downloading=true 当作未安装。

## 6. 读取、错误与重复项

- config.ini 限制 64 KiB，支持 UTF-8 BOM、CRLF、未知节/键，必须完整读取；重复关键字段、截断及编码错误归为无效元数据。
- 使用只读打开和文件元数据前后检查；在结果生成前再次读取关键内容、候选 GameBiz/路径，变化时重试一次。不是跨注册表/文件的事务快照，文档明确仍存在外部文件变化窗口。
- 缺失注册表键、游戏目录和提交文件属于正常无结果；权限错误/损坏配置记录现有日志并跳过该候选，不影响其他有效游戏。
- 所有注册表来源均不可访问时返回扫描错误，不伪装成正常空列表。
- 同 biz、同规范化路径合并；不同路径先核验，优先当前用户已验证渠道的确定顺序。仍有多个有效安装时记录冲突并按规范化路径稳定选择，保证 games/find 一致；不按扫描偶然顺序覆盖。
- 默认不遍历资源、不计算全量哈希。只读已知注册表根、小配置和指定文件元数据，耗时随登记候选数增长。

## 7. 接入位置

核心：src/lib.rs 导出 hoyoplay；src/prelude.rs 增加 HoYoPlay 和字符串转换。

C FFI：复用现有 list/find/executable 分发，增加 hoyoplay 字符串识别和头文件平台说明；不改变 Game JSON、函数签名或内存释放约定。

Node：新增 node/src/types/hoyoplay.rs，沿用 wegame 的包装；更新导出和 node/lib/index.d.ts，不增加 Game 字段。

GUI：新增平台标签和类型；Rust commands 分发增加三项操作；capability 仅 List/Find/Executable。可执行路径显示为启动器路径，游戏 path 为游戏根目录，界面不增加进程名或下载任务列。

文档/示例：增加 examples/hoyoplay.rs、README 支持范围及 docs/hoyoplay.md。现有调研证据保留独立文档，不作为运行时依赖。源码发行 include 配置需覆盖新增 Rust 文件；若选择外部数据格式目录快照，须同步纳入 crate 打包，优先用小型 Rust 常量避免遗漏。

## 8. 验证与实施顺序

### A. 实现前必须验证

1. 第二款游戏：同样记录首次下载、解包/校验、安装完成；验证 game_version 的提交时机和官方启动文件配置。
2. 绝区零：验证启动器重开后候选和提交记录仍可读取，以及无启动器进程时离线检测的可行性。
3. 已安装更新/预下载：确认本地旧版安装记录与首次安装记录可区分；缺少可用更新样本时明确保留该场景的覆盖缺口，不能宣称完成全部状态支持。
4. 对本机数据的暂停、退出、修复、移动或卸载操作需用户另行授权；不为取样改变正在使用的安装。删除/残留/损坏通过独立临时目录测试，不改真实游戏。

若主判据不成立，返回调研阶段；不以一个“只适用于绝区零”的临时公开实现填补验证缺口。

### B. 判据通过后的实现

先实现私有候选和校验及测试，再完成核心三个函数，最后接 FFI、Node、GUI。绑定层仅分发，不再解释安装条件。无需先修改所有消费者来展示未验证结果。

### C. 有意义的自动化验证

- 下载期与完成期实测转换为脱敏 fixture：同一候选首次下载不返回、提交完成后返回。
- 未安装默认目录、注册表残留、空版本、只有 EXE、只有版本、无效渠道、配置冲突、路径逃逸及单个损坏候选不污染其他游戏。
- 已有旧版 + 新版下载场景用实测规则测试；不构造假设来“证明”未验证协议。
- 中文/空格路径、32/64 位视图去重、多个有效目录的稳定选择、扫描期间配置变化。
- 对外验证 Game 字段和 ID 一致、未知 ID 错误、平台分发、GUI capability；Node/FFI 冒烟读取相同结果。
- 执行 workspace tests、Node 构建、GUI check/build、FFI 构建及现机只读冒烟。仅构建不等于验证未知游戏和状态，文档报告实际覆盖范围。

## 9. 当前决策

方案采用小 Interface 和模块内集中校验；首选不依赖 gamedata 二进制和下载数据库的最小提交证据组合。已有明确实现路线，但完成前置状态验证后才把判据作为产品能力开放。此文档不授权添加临时检测逻辑，也不将尚未验证的国际服、其他游戏或更新场景标记为已支持。
